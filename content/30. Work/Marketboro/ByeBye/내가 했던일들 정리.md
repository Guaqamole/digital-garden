
## 1. 검색 v2 시스템 개편
### 문제점
- 사용자의 검색 의도대로 검색이 되지 않음
- 오렌지 입력시 오렌지만 나오는것이 아닌, 치즈, 쌀이 섞여서 나온다
- 전체적인 데이터 중 특정 데이터를 우선적으로 보여주는 elasticsearch Function_score가 너무 복잡함
- score = ‘<상품명>*w1 + <업체명1>*w2 + <업체명2>*w3 + <상품카테고리명>*w4’ 와 <키워드> 일치도 계산 (w1>w2>w3>w4)
- 정확도 순, 가격 낮은 순 등 정렬 순서마다 추가적인 score를 계산하여 검색 결과를 리턴 예) score * 판매량
- 문제는 검색 이슈가 인입될때마다 복잡한 Score를 업데이트하는 과정을 모두 수동으로 했기때문에 장애가 나는 상황이 빈번했다.

**문제점 정리**
1. 복잡하게 짜여진 function score 떄문에 사용자의 검색 의도대로 검색이 되지 않음
2. CS가 인입될때마다 모든걸 수동으로 수정하고 배포하여 휴먼에러 발생 가능성 증가
3. 하나의 노드에서 모든 Role을 맡고 있었기 떄문에 검색량 증가시 Role 분리 필요

### 문제를 해결하기 위해 필요했던일들
- 검색 알고리즘 변경
- 검색 인프라 변경
- 검색 배포 플로우 자동화

	- 동의어, 유의어 사전 파일관리 X, 동적으로 관리
	- 노드간 역할 분리
	- EC2 → EKS 이관
- 검색 배포 자동화
	- 동의어, 유의어 사전 S3 자동 업로드
	- INDEX TEMPLATE → argo cd + bitbucket pipeline

## 2. 검색 색인 개선
### 문제점
- 식봄에서는 식자재 상품 정보를 ES에 색인하여 Serving API를 통해 상품 정보를 받아왔다.
- 따라서 상품 정보를 색인하기 위해 DB에 존재하는 상품 정보, 상품 통계등 검색 결과에 필요한 모든 결과를 DB 쿼리로 처리하여 Airflow로 10분마다 ES로 ETL 하였다.
- 하지만 Local Executor로 구성된 Airflow이다 보니 특정 시간대 스케줄링된 Job이 하나의 워커에 몰리게 되면 OOM Kill 에러가 자주 발생하여 서비스에 직접적인 영향을 끼치는 색인은 별도로 분리하기로 결정.
- 또한 색인 시간이 너무 긴탓에 수량등 상품 정보가 정확하지 않아 주문시 품절 된 상품이 포함된적이 많았다.

- 색인 프로세스 분리
- 색인 시간 단축
- 유지 가능한 코드로 만들기

- Spring Batch
