# MongoDB 소개

## 손쉬운 사용

**도큐먼트 지향 데이터베이스의 핵심 특징**
- 관계형 DB의 row 대신 **도큐먼트**(document) 사용 → JSON-like 구조로 계층 관계를 단일 레코드로 표현 가능
- 내장 도큐먼트와 배열 허용 → 복잡한 계층 관계(hierarchical relationship)를 하나의 레코드로 표현
- 객체 지향 언어(Java, Python)의 데이터 구조와 자연스럽게 대응 → User 객체 안에 Address 리스트를 포함하는 구조와 동일
- 관계형 모델 미사용의 주된 이유: **분산 확장**(scale-out)을 쉽게 하기 위함 (JOIN 없는 구조가 샤딩에 유리)

**스키마리스(Schemaless) 설계**
- 도큐먼트의 키와 값을 사전 정의하지 않음 → 고정된 스키마 없음
- 필요시 필드 추가/제거 자유로움 → 개발 과정 빠른 반복, 모델 실험 용이
- 개발자가 수십 개의 데이터 모델을 시도한 후 최선의 모델 선택 가능

### 왜 스키마리스가 필요한가?

**관계형 DB의 스키마 변경 비용**
- 테이블 구조 사전 정의 필수 → 컬럼 타입과 제약조건 엄격히 강제
- 데이터 일관성에는 유리하지만, 요구사항 변경이나 프로토타이핑 시 개발 속도 저하
- MySQL에서 컬럼 추가 시 `ALTER TABLE` 실행 필요 → 대용량 테이블은 수분~수시간 락(lock) 발생
- DB 레벨 마이그레이션 불가피 → 배포 복잡도 증가

**MongoDB의 유연성**
- 같은 컬렉션 내에서도 도큐먼트마다 다른 필드 구조 허용
- 신규 필드 필요시 애플리케이션 코드에서 바로 삽입 → DB 레벨 마이그레이션 불필요
- 애자일 개발 환경에서 특히 유용 → 스프린트마다 스키마 변경 가능

**Trade-offs (대가)**
- 스키마 검증이 DB 레벨에서 불가 → 데이터 일관성은 전적으로 애플리케이션 레이어에서 보장해야 함
- 시간이 지나면 컬렉션 내 도큐먼트 구조 파편화 위험 → 쿼리 로직 복잡화, 예상치 못한 버그 유발
- MySQL처럼 잘못된 타입 삽입을 DB 레벨에서 막지 않음 → 런타임 에러 가능성 증가
- MongoDB 3.2부터 document validation 제공하지만 기본적으로 비활성화 → 선택적 스키마 강제 가능하나 명시적 설정 필요

### 내장 도큐먼트와 계층 구조

**관계형 DB의 JOIN 방식**
- 1:N 관계 표현 시 테이블 분리 + 외래키(foreign key) 사용 (예: `users`와 `addresses` 테이블)
- 정규화(normalization) 원칙에 부합하지만, 데이터 조회시마다 JOIN 연산 필요
- JOIN 비용은 데이터 증가에 비례하여 증가 → 읽기 성능 저하

**MongoDB의 내장 도큐먼트 (Embedded Document)**

```javascript
{
  _id: ObjectId("507f1f77bcf86cd799439011"),
  name: "John Doe",
  email: "john@example.com",
  addresses: [
    { street: "123 Main St", city: "Seoul", zipcode: "12345" },
    { street: "456 Oak Ave", city: "Busan", zipcode: "67890" }
  ]
}
```

**내장 방식의 장점**
- 사용자와 주소 정보를 단일 도큐먼트로 저장 → JOIN 없이 한 번의 쿼리로 모든 정보 조회
- 읽기 성능 크게 향상 (단일 쿼리 vs 다중 JOIN)
- 객체 지향 언어의 데이터 구조와 정확히 일치 → 직렬화/역직렬화 오버헤드 최소화

**내장 방식의 Trade-offs**
- 주소 정보가 매우 많거나 자주 변경되면 도큐먼트 크기 증가 → 업데이트 비용 증가 (전체 도큐먼트 재작성)
- 도큐먼트 최대 크기 16MB 제한 → 초과시 데이터 분할 필요 (GridFS 또는 참조 방식으로 전환)
- 여러 사용자가 동일 주소 공유시 (예: 회사 주소) 중복 데이터 발생 → 스토리지 낭비, 일관성 문제
- 이런 경우 관계형 DB처럼 참조(reference) 방식이 더 적합 (`ObjectId`로 연결, 수동 조인)

### 언제 MongoDB를 사용하고, 언제 사용하지 말아야 하는가?

**MongoDB가 적합한 경우**
- 빠른 프로토타이핑과 반복적 스키마 변경이 필요한 스타트업 환경
- 비정형 데이터나 중첩된 계층 구조(JSON-like) 저장 필요 (예: 소셜 미디어 포스트, 이벤트 로그)
- 읽기 성능이 중요하고 JOIN 연산 최소화가 목표일 때 (내장 도큐먼트 활용)
- 수평 확장(샤딩) 필요한 대규모 분산 시스템 → sharding 통해 write throughput 확보
- 로그, 이벤트, 세션 데이터처럼 쓰기가 많고 엄격한 트랜잭션 불필요한 경우

**MongoDB를 피해야 하는 경우**
- 복잡한 다중 테이블 JOIN과 ACID 트랜잭션이 필수적인 금융 시스템 (결제, 송금, 회계)
- 정규화된 데이터 구조가 명확히 정의된 레거시 시스템과의 통합 → 스키마 불일치 문제 발생
- 도큐먼트 간 강한 일관성 보장 필요시 (MongoDB 4.0부터 다중 도큐먼트 트랜잭션 지원하나 성능 오버헤드 큼)
- SQL 분석 쿼리와 복잡한 집계(aggregation)가 주된 워크로드인 경우 → PostgreSQL이나 분석 전용 DB(ClickHouse, BigQuery)가 더 효율적
